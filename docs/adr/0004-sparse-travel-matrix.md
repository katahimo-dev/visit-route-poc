# ADR-0004：移動時間行列は近傍の区間だけ地図APIで実測し、残りは概算で埋める

- 日付：2026-10-10
- 状態：採用

## 背景
AI案の入力の移動時間行列（地点 n × n）を、全区間 Routes API に聞いていた。課金は n² 要素（TRAFFIC_AWARE は上位SKU）で、
キャッシュに1区間でも欠けがあると全行列を取り直す、ルートなし（NO_ROUTE）の区間を毎回取り直す、途中で失敗すると課金済みの結果を捨てる、
地点数の上限がない、という問題があった（コードレビュー指摘）。
一方、遠い区間は最適解（割当と順番）にまず入らないので、全区間が正確である必要はない。

## 選択肢
1. 案A：近傍の区間だけ Routes API で実測し、残りは直線距離の概算を実測から補正して埋める（疎な行列）
2. 案B：全区間を OSRM などの自前の経路エンジン（OpenStreetMap）で作り、Google は使わない、または検証だけに使う
3. 案C：概算の行列で解き、AI案で使われた区間だけ Routes API で検証して解き直す（2段階）
4. 案D：今のまま全区間を取り、キャッシュの欠けだけ直す

## 決定
案A。あわせて、キャッシュは足りない区間だけ取得し、ルートなしも覚える。
- 実測する区間：各地点から直線距離で近い10地点（どちらか一方の近傍に入れば両向き）。地点が11以下なら全区間
- 課金の天井：1回の行列作成で地図APIに聞くのは1,000要素まで。超える分は近い区間を残して概算にする
- 近傍外の区間：直線距離×1.3を平均速度で割った概算に、同じ行列の実測区間の「実測÷概算」の中央値を掛ける（1〜3倍に制限。1未満にしない）
- 取得：出発地1つ×足りない到着地だけを1リクエストにする（余計な要素を課金させない）。成功したリクエストごとにキャッシュへ書く
- キャッシュの時間区分：時（24区分、UTC）から、補正モデルと同じ時間帯（朝・日中・夕方、日本時間）に変更

## 理由とトレードオフ
- 得るもの：課金が n² から約 n×k に下がる（60地点で約3,500要素→600要素前後）。キャッシュの読み取りも同じだけ減る。地点数が増えても課金に天井がある。インフラを増やさない。
- 失うもの：近傍外の区間は概算。ソルバーが近傍外の区間を選ぶと、その区間の予測は地図APIの値ではない（`source: estimate`）。概算は実際より短くならないよう倍率を1以上にしているので、遠い区間を選びにくい側に倒れる。
- キャッシュの時間区分を粗くしたので、同じ時間帯の中の混み具合の差は区別しない（補正モデルも同じ区分なので整合する）。

## 影響
- design.md §3 travel-time の責務・完了の条件を更新。`predictMatrix` の入出力は変わらない。
- 以前のキャッシュ（時単位のキー）は使われなくなり、30日で期限切れになる。
- 見直す条件：1回目の実証で、AI案に近傍外の区間が多く入る、または予測誤差（±10分以内90%）を外す原因が概算区間にある場合は、案C（使われた区間の検証）を足す。
- 次の段階（提案）：案B を仙台市の範囲に限って試す。OSRM に OpenStreetMap の宮城県（または仙台市周辺）のデータを入れて Cloud Run に置き、全区間の基準値を自前で作る。渋滞は持たないので、実測から学習する補正モデル（travelModels）で補う。採用するときは別の ADR にする。
