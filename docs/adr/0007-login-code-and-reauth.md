# ADR-0007：ログインはメールの6桁コード、使わなかった日数で再認証、デモ用ログイン

- 日付：2026-10-10
- 状態：採用

## 背景
- ログインはメールリンク（Firebase 標準）だった。スタッフはスマホのホーム画面に追加した PWA で使うが、iPhone ではホーム画面のアプリと Safari でログイン状態が別々で、メールのリンクは Safari 側で開くため、アプリがログインできない。
- 一度ログインすると期限なく続く。端末に訪問先の住所などを保存したまま、ログアウトしても消えなかった。
- 管理者は PC で全スタッフ・全訪問先を扱い、事務所で共用されやすい。
- 実証の説明会で、画面をすぐに試してもらう手段が要る。

## 選択肢
1. ログイン方法
   - 案A：メールの6桁コード（業務関数で発行・照合し、カスタムトークンでログイン）
   - 案B：メールリンクのまま
   - 案C：Google アカウント／パスワード
2. ログインの期限
   - 案A：使わなかった日数で再認証（スタッフ14日、管理者・運営者3日）
   - 案B：ログインから一定時間で必ず再認証（管理者12時間など）
3. デモ
   - 案A：デモ期間だけ、メールなしで架空の事業所に入れるボタン
   - 案B：共有のデモ用メールアドレスとコードを配る

## 決定
- ログイン：案A。全員（スタッフ・管理者・運営者）コードに統一する。
  - コードは10分有効、5回間違えたら無効、使い捨て。送信は同じアドレスへ60秒あけ、1時間に5回まで
  - 招待済み（クレームあり）のアドレスにだけ送る。応答は、未招待・送信の上限に当たったときも同じで、最低800ミリ秒待ってから返す（応答時間の差でも探らせない）
  - 1アドレスで24時間に15回間違えたら、24時間はコードを出さず照合もしない（長期・複数アカウントへの総当たり対策）
  - コードの文書と送信したメールは `expireAt` を付け、Firestore の TTL で1日後に消す。件名にはコードを入れない（ロック画面の通知に出るため）
  - コードはハッシュ（ランダムな salt つき）で `loginCodes/{メールのハッシュ}` に置き、ログに出さない（エミュレーターだけ出す）
  - メールは `mail` コレクションに書き、拡張機能 Trigger Email が SMTP で送る
- 期限：案A。毎晩 `revokeInactiveSessions` が、最後にトークンを更新した時刻から日数が過ぎた人のリフレッシュトークンを無効にする。毎日使う人は止まらない
- 端末のデータ：スタッフだけオフライン用に保存し、ログアウト・再認証切れで消す（未送信の記録があれば確かめる）。管理者・運営者は保存しない
- デモ：案A。実証用プロジェクトをまずデモ期間として使い、評価と調整のあとデモを外して実データの検証に切り替える（同じプロジェクト。README「デモ期間から本番への切り替え」）。
  - `DEMO_ORG_ID` を設定した環境だけ `demoSignIn` が動き、入れるのはデモの印（`demo: true`、seedDemo だけが付ける）のある事業所だけ。設定を誤っても実データの事業所には入れない
  - 画面は `VITE_DEMO_LOGIN=true` のビルドだけボタンを出す
  - デモの入口に簡易パスワードを置く（2026-10-11）。`demoStaffList`・`demoSignIn` はパスワードを受け取り、Secret Manager の `DEMO_PASSWORD_HASH`（固定の前置き＋SHA-256。`scripts/demoPasswordHash.ts` で作る）と照合する。リポジトリは公開なので、パスワードもハッシュもリポジトリに置かない（弱いパスワードはハッシュから総当たりで戻せる）。未設定ならデモに入れない。間違えたら少し待たせる。不特定多数・検索エンジン経由のアクセスをはじくだけのもので、アカウントの保護ではない（パスワードは説明会などで口頭・資料で伝える）
  - デモのスタッフは常にデモ用のアカウント（実在のアカウントのクレームを書き換えない）
  - スタッフは誰として入るかを選べる。選ぶための一覧 `demoStaffList` は未ログインで呼べるが、返すのは seed が作ったスタッフ（ID が s1〜s20）の名前とその日の訪問件数だけ。デモの管理者が足したスタッフはログイン画面に出さず、読む量も増えない（名前はデモの管理者が書き換えられるので、入れ直しの seed で戻す）
  - デモ期間は `inviteMember` を止め、`requestLoginCode` は運営者（スクリプトで作った人）にだけ送る（誰でも管理者になれるので、他人のアドレスへの送信の踏み台にしない）。地図APIのキーは置かない
  - 切り替えは `scripts/endDemo.ts` で、デモの事業所と、デモ・@example.com のアカウントを消してから行う。デモ期間と実データの期間は重ねない

## 理由とトレードオフ
- 得るもの：PWA から出ずにログインできる。放置された端末だけが再認証になる。デモはメールなしですぐ試せ、実データの事業所には入れない。
- 失うもの：メール送信の仕組み（拡張機能と SMTP）を用意する必要がある。コードは口頭で聞き出されうるので、メール本文で注意する。管理者の二要素認証はまだない（次の対応）。
- 再認証の判定は毎晩なので、日数を過ぎてから最長1日と、ID トークンの有効期限（最長1時間）は使える。
- 事務所の PC で管理画面を開いたままにすると、使っている扱いになり切れない。管理者の二要素認証（次の対応）と運用（離席時に閉じる）で補う。
- 再認証切れのとき、端末に残った未送信の記録は消える（ログインしていない状態ではルールで拒まれ、送れないため）。14日使っていない端末に未送信が残ることはまずない。
- App Check（正規のアプリからの呼び出しだけを通す仕組み）は未導入。総当たり・乱発がさらに問題になれば入れる。

## 影響
- design.md §3（L2）・§4 org・§5 API・§6 の認証。README のデプロイ手順。
- 運用：業務関数のサービスアカウントに `roles/iam.serviceAccountTokenCreator`（カスタムトークンの署名）。Trigger Email 拡張機能の設定。
- 見直す条件：メールが届かない・迷惑メールに入る苦情が多ければ、SMS（電話番号認証）を検討する。
