# ADR-0006：スタッフに見せる情報の絞り込み、退職時の即時遮断、課金の天井

- 日付：2026-10-10
- 状態：採用

## 背景
main 全体のコードレビューで、次の指摘があった。
- スタッフが同僚のスタッフ文書（自宅・メール）と、訪問先の NG スタッフを読める（PRD §7 の「氏名・住所の分離、最小限の個人情報」に反する）
- スタッフを休止（active=false）にしても、別の人に付け替えても、古いアカウントのクレームが残り読み書きできる
- 記録（events）の作成に上限がなく、勤怠の再計算 → 実測区間 → 地図API の連鎖が際限なく起きうる
- 関数のインスタンス数・AI案の作成回数に上限がない。同じ requestId の二重実行が起きうる。住所変換を毎回地図APIに聞く

## 選択肢
1. 案A：ルールとデータの持ち方で絞る（スタッフ文書は本人だけ、NG は管理者だけの文書に分ける、ルールでスタッフ文書の active と uid を見る）＋関数側に天井を設ける
2. 案B：スタッフ向けの読み取りをすべて関数経由にし、必要な項目だけ返す
3. 案C：クレームの付け外しだけで対処する（ルールは変えない）

## 決定
案A。
- `staff`：スタッフが読めるのは自分の文書だけ（管理者・運営者はすべて）
- 訪問先の NG スタッフは `clientPrivate/{clientId}`（`ngStaffIds` だけ。管理者・運営者だけが読み書き）に分ける。`clients` に `ngStaffIds` は書けない
- スタッフの読み書きは、クレームに加えて「スタッフ文書が active で、uid が本人」のときだけ通す（ルールの `isActiveStaff`）。休止・付け替えはその場で効く
- 休止に変わったとき・付け替えたときは `onStaffUpdated`（と `inviteMember`）が古いアカウントのクレームを外し、リフレッシュトークンを無効にする。外すのはクレームの staffId がそのスタッフと一致するときだけ（別のスタッフに付け替え済みの人は外さない）。再開するときは招待し直す
- 記録の端末時刻は「7日前〜10分先」だけ受け付ける
- 勤怠候補は中身が変わらなければ書かない。実測区間は到着・退出などの時刻が変わったときだけ作り直す
- 全関数に `maxInstances: 10`。AI案は1事業所1時間およそ20回まで（`planRunLocks` で数える。数えてから作るので、同時に押すと少し超えうる概数の天井）。同じ requestId は `planRunLocks` の create で原子的に1回だけ実行する。関数がタイムアウトで止まると鍵が残り、その requestId は再実行されない（画面は毎回新しい requestId を送るので実害はない）
- 住所変換の結果は `geocodeCache` に30日置く

## 理由とトレードオフ
- 得るもの：画面の作りを大きく変えずに、スタッフに見える情報と、辞めた人の権限を絞れる。課金に天井ができる。
- 失うもの：スタッフの読み書きのたびに、ルールがスタッフ文書を1回読む（読み取り1回分の課金）。訪問先の保存が2文書になる。
- 関数（Callable）は ID トークンの有効期限（最長1時間）まで古いクレームで通る。Firestore はルールで即時に止まるので、勤怠の訂正など関数だけの操作が最長1時間残る。
- 管理者アカウントの剥奪は対象外（運営者が手で行う）。

## 影響
- design.md §4 の org・planning・field の持つデータ、§5 のエラー（RESOURCE_EXHAUSTED）。
- 既存データの移行：`clients` の `ngStaffIds` を `clientPrivate` に移す（α版の本番データはまだないので、デモデータの作り直しで足りる）。
- 見直す条件：スタッフ画面で同僚の名前・連絡先が必要になったら、表示用の項目だけを持つ別コレクションを作る。
