# ADR-0008：スタッフの稼働時間帯は「基本の曜日と時間」＋「日ごとの上書き」で持つ

- 日付：2026-10-11
- 状態：採用

## 背景
ヘルパーの勤務は曜日と時間で固定ではなく、個別の休み・時間休・休日出勤がある（PRD R18）。
これまではスタッフ文書の `workDays`・`shiftStart`・`shiftEnd`（1日1区間）だけで、日ごとの違いを表せなかった。
決まっていること（2026-10-11）：
- 区分（年休・時間休など）は持たず、その日に働ける時間帯だけを持つ。30分単位。1日に複数の時間帯がある（時間休＝途中の抜け）
- 管理者はカレンダーで一覧・編集、スタッフは自分の分をアプリで当日も含めて変えられる。承認なしですぐ反映し、管理者には本人が変えた印を見せる
- 予定画面は時間外の割当を警告するだけ。AI案は時間帯を守る

## 選択肢
1. 案A：基本はスタッフ文書のまま。違う日だけ `availability/{staffId}_{date}` に、その日の時間帯の配列を置く（無ければ基本）
2. 案B：毎日の時間帯をすべて展開して持つ（基本を変えたら先の日を書き直す）
3. 案C：スタッフ文書に「日付 → 時間帯」の地図を足す

## 決定
案A。

- 文書：`availability/{staffId}_{date}` ＝ `{ staffId, date, slots: [{start, end}], byStaff, updatedBy, updatedAt }`
  - `slots` は開始の順・重なりなし・30分単位・最大4つ。空の配列は「その日は休み」
  - 文書を消すと基本に戻る
- その日の時間帯を決める関数は1つ（`packages/shared` の `availabilityOf`）。画面・予定の警告・AI案で同じものを使う
- 書ける人（firestore.rules）
  - 管理者：自分の事業所の全員・全日
  - スタッフ：自分の分だけ、日本時間のきょう以降。`byStaff: true` を必ず付ける
- 最適化サービス：勤務時間は最初の時間帯の開始〜最後の時間帯の終了とし、あいだの抜けを休み（`breaks`）として渡す
  - 訪問は休みに重ならない。移動は休みにかかってもよい（休み明けに向かう移動を許すため）

## 理由とトレードオフ
- 得るもの
  - 基本を変えれば先の日すべてに効く。違う日だけを書くので文書が少ない
  - スタッフが書けるのは自分の上書き文書だけで、スタッフ文書（自宅・NG に関わる設定）を書かせなくてよい（ADR-0006）
- 失うもの
  - 基本を変えても、すでに上書きした日はそのまま（カレンダーで上書きの印を見て判断する）
  - 「休み」と「基本どおり」が文書の有無と空配列で分かれるので、読む側は必ず `availabilityOf` を使う
- 案B は基本を変えるたびに先の日を一括で書き直す必要があり、手で直した日との区別もつかない
- 案C はスタッフにスタッフ文書の書き込みを許すことになり、1文書が際限なく大きくなる

## 影響
- design.md：org が `availability` の持ち主。schedule（予定の警告）と planning（AI案の勤務時間）が読む
- API：optimizer の `StaffInput` に `breaks`（任意）を足す（後方互換）
- 費用：予定画面・カレンダーで期間の上書き文書を読むだけ（1か月×8人で最大240件）
- 見直す条件：区分や日数の管理（年休の残日数など）が要るとわかったとき。そのときは勤怠の領域として別に設計する
