# ADR-0001：データ基盤に Firebase（Firestore）を使い、事業所を orgs/{orgId} で分ける

- 日付：2026-10-10
- 状態：提案

## 背景
実証用PoCを150h・約1か月で協力法人に渡す。スタッフは電波の弱い場所でも記録し、後で1回だけ送る必要がある。3事業所のデータは互いに見えてはならない。提案書の経費（クラウド 30,000円）は Firebase / Google Cloud を前提にしている。

## 選択肢
1. 案A：Firebase（Auth・Firestore・Functions・Hosting）、1プロジェクトに全事業所、`orgs/{orgId}` 配下＋カスタムクレーム＋セキュリティルール
2. 案B：katahimo-app と同じ PostgreSQL（Cloud SQL）＋ RLS
3. 案C：事業所ごとに Firebase プロジェクトを分ける

## 決定
案A。

## 理由とトレードオフ
- 得るもの：オフライン保存と再送・リアルタイム更新・メールリンク認証が標準。サーバー運用なし、待機費用ほぼ0。画面からの直接読み書きで工数を減らせる。
- 失うもの：結合・集計クエリが弱い（分析は CSV で外に出す）。ルールが事業所分離の唯一の砦になる（エミュレーターテスト必須）。katahimo-app とコードを共有できない。

## 影響
- 全コレクションを `orgs/{orgId}` 配下に置き、ルールは `request.auth.token.orgId == orgId` を必ず確認する。運営者（operator）だけ全事業所を読める。
- ルールのテスト（別事業所が読めない・スタッフが他人の記録を書けない）を CI で回す。
- 見直す条件：本格運用（R9以降）で事業所数が増え、集計・請求連携が必要になったら PostgreSQL への移行を検討する。
