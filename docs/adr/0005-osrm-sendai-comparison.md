# ADR-0005：OSRM（OpenStreetMap）の仙台版を立て、実測区間で Google と並べて比べる

- 日付：2026-10-10
- 状態：採用

## 背景
移動時間の基準値は Google Routes API（有償）で取っている（ADR-0004 で近傍だけに絞った）。
OpenStreetMap の経路エンジンなら全区間を無料で作れるが、渋滞情報を持たない。
KPI（予測誤差±10分以内90%）を外す主因が渋滞なのか、駐車・徒歩など地図の外の要素なのかは、実測が溜まるまで分からない。
どちらを基準値に使うかは推測で決めず、1回目の実証の実測区間で比べて決めたい。

## 選択肢
1. 案A：OSRM（車）を仙台市周辺に限って Cloud Run に置き、実測区間に OSRM の値も並べて残す。予測には使わない
2. 案B：Valhalla を置く（時間帯別の速度データを入れられる）
3. 案C：比べずに Google のまま続ける

## 決定
案A。
- 範囲：Geofabrik の東北地方データから、仙台市と周辺（経度140.20〜141.10、緯度38.00〜38.50。名取・多賀城・塩竈・富谷を含む）を切り出す
- 移動手段：車（car プロファイル）だけ。自転車・徒歩は比べない（必要になったら同じ Dockerfile のプロファイル違いで足す）
- 置き場所：Cloud Run（`osrm/`、IAM 認証、最小0・最大2インスタンス）。業務関数のサービスアカウントだけが呼べる
- 記録：`legActuals` に `osrmSeconds`・`osrmMeters`（未設定・非対応・失敗は null）と `straightMeters`（直線距離）を足す。実証データCSV（移動時間_予測と実測）に「OSRM秒」「直線距離m」の列を足す
- 比較：`analysis/compare_travel_time.py` で、直線距離の概算・Google基準・Google予測・OSRM・それぞれ×補正（日ごとの交差検証）を、±10分以内の割合などで並べる

## 理由とトレードオフ
- 得るもの：Google をやめられるかどうかを、実データで判断できる。OSRM の運用費は Cloud Run の最小0インスタンスでほぼゼロ。
- 失うもの：Cloud Run のサービスが1つ増える（地図データの更新はイメージの作り直し）。実測区間1件ごとに OSRM を1回呼ぶ。
- Valhalla は渋滞の速度データを自前で用意しない限り OSRM と精度が変わらないので見送る。

## 影響
- design.md：L2 に経路エンジン（OSRM）、travel-time の依存と `legActuals` の項目、§7 の表を更新。
- 地図データは © OpenStreetMap contributors（ODbL）。画面に OSRM の値を出すときは表記が必要（今回は分析だけなので画面には出さない）。
- 再現：イメージのタグ（作成日）が地図データの版。イメージ内の `/data/data_date.txt` に元データの日付を残す。
- 見直す条件：1回目の比較で「OSRM×補正」が「Google予測」と同等（±10分以内の割合の差が数ポイント以内）なら、基準値を OSRM に切り替える ADR を立てる。差が大きければ OSRM を止める。
