# 個人開発のための抽象化・アーキテクチャ設計

人間が「抽象」（何を・どう分けて・何を約束するか）を決め、実装をAIコーディングエージェントに任せられる状態をつくるスキル。

- 原則：**詳細を隠し、意図を表す。** 境界と契約は厳密に、中身は自由に。
- 役割分担：設計の**案**はAIが出す。何を優先し何を捨てるかの**判断**はユーザーが行う。
- 不明点は推測で埋めない。質問としてまとめてユーザーに返す。

## フォルダ構成

```
solo-architecture-design/
├── SKILL.md                 … この手順書
├── references/              … 必要なときだけ読む詳細資料
│   ├── c4-diagrams.md       … C4の各レベルで描くもの・描かないもの、Mermaid例
│   ├── api-design.md        … リソース指向API、標準メソッド、エラー、互換性、冪等性
│   ├── principles.md        … SOLID / IDEALS、漏れのある抽象化、過剰な抽象化
│   ├── decision-guide.md    … 粒度・モノリス/マイクロサービス・先に決めることなどの判断基準
│   └── review-checklist.md  … 設計レビューの観点と判定基準
├── templates/               … プロジェクトにコピーして埋めるひな形
│   ├── prd.md / design.md / adr.md / agents.md / handoff.md / openapi.yaml
├── scripts/
│   ├── init_design.py       … プロジェクトに docs/ と AGENTS.md のひな形を作る
│   ├── check_design.py      … 設計書の不足・縮尺の混在・未決事項を検査する
│   ├── check_openapi.py     … OpenAPIの契約の抜け（エラー定義・命名など）を検査する
│   └── make_handoff.py      … 設計書からコンポーネント別のAI作業指示書を生成する
└── examples/bookstore/      … オンライン書店の記入例（PRD・設計書・OpenAPI）
```

スクリプトは Python 3 標準ライブラリで動く（OpenAPIのYAML読込のみ PyYAML があれば使い、なければJSONで扱う）。
`<skill>` はこのスキルのフォルダの絶対パスを指す。

## モードの判定

| ユーザーの依頼 | モード |
|---|---|
| 新しく作りたい・機能を追加したい・設計書を作って | **設計モード** |
| 設計書を見て・このアーキテクチャどう？・レビューして | **レビューモード** |
| 「分けるべき？」「マイクロサービスにすべき？」「APIを変えたい」など判断の相談 | **相談モード**：`references/decision-guide.md` を読んで答える |
| AIエージェントに実装を振りたい | **引き渡しモード** |

## 設計モード

規模に合わせて深さを変える。個人開発の最低ラインは **PRD・L1/L2の図・API一覧・AGENTS.md**。

### 0. 準備
- プロジェクトに `docs/` がなければ：`python3 <skill>/scripts/init_design.py <プロジェクトのパス>`
  （既存ファイルは上書きしない。作成したファイル一覧が表示される）
- 既存コードがある場合は、先にディレクトリ構成・主要エントリポイント・DBスキーマ・外部連携を読み、現状をL1/L2として書き起こしてから変更を設計する。

### 1. PRDを固める（何を・なぜ）— `templates/prd.md`
- ユーザー、解決する課題、要件、成功の指標、**やらないこと**を確認する。
- 要件文から **名詞（業務データ）** と **動詞（業務の処理）** を抜き出して表にする。これがAPIの骨格になる。
- 意図があいまいな点はここで質問する。設計に進んでから推測で埋めない。

### 2. 縮尺を決めて図を描く — `references/c4-diagrams.md`
- L1 システムコンテキスト：誰が使い、どの外部システムとつながるか。**技術名は書かない。**
- L2 コンテナ：実行される単位（Webアプリ・API・DB・関数など）と技術選定・通信方式。※Dockerのコンテナとは別概念。
- L3 コンポーネント：コンテナ内の機能のまとまり。**AIエージェントに仕事を分ける単位。** 小規模なら省略可。
- L4 コード：原則描かない。重要なインターフェースだけ。
- 図はすべて Mermaid で書く（Gitで差分管理でき、AIも読める）。

### 3. 境界を引く — `references/decision-guide.md`
分け方の3つの目安：
1. 変更の理由が同じものはまとめ、別々に変わるものは分ける
2. データの持ち主（書き換えてよいコンポーネント）は1つ。他はAPI経由で参照
3. 1つのAIエージェントのセッションで全体を把握できる大きさ

構成は **モジュラーモノリス（1つのアプリ内に境界とAPI）** を既定とし、独立デプロイ・負荷特性の違い・担当分離が必要になったら切り出す。

### 4. API契約を書く — `references/api-design.md` / `templates/openapi.yaml`
- リソース（名詞）を階層で定義：`/users/{user_id}/orders/{order_id}`
- 他リソースは中身を持たず「一意な名前（ID）」で参照
- まず標準メソッド（Create / Get / List / Update / Delete）。無理なときだけカスタムメソッド
- 入出力・**エラーの種類と意味**・タイムアウト・再試行可否（冪等性）を書く
- エラーは業務の言葉で返す（DBの内部エラーを漏らさない）
- 書いたら検査：`python3 <skill>/scripts/check_openapi.py docs/api/openapi.yaml`

### 5. 設計書にまとめる — `templates/design.md`
8セクション（背景と目的／やらないこと／全体図／コンポーネントと責務／API契約／デプロイ構成／代替案とトレードオフ／未決事項）。数ページで十分。
関数ごとの処理手順・変数名・細かなクラス設計は書かない。
大きな判断（DB選定、同期/非同期、分割など）は `templates/adr.md` でADRとして残す。
書いたら検査：`python3 <skill>/scripts/check_design.py docs/design.md`。エラーは直し、警告は内容を確認する。

### 6. ユーザーの判断をもらう
設計案に代替案がある箇所は、選択肢・トレードオフ・推奨を短く示し、ユーザーに決めてもらう。決定と理由は設計書の「代替案とトレードオフ」に記録する。

## 引き渡しモード（AIエージェントへの作業指示）

コンポーネントごとに **4点セット** を渡す：
1. **担当範囲**：作るコンポーネントと、触ってはいけない範囲
2. **守るべき契約**：該当するAPI定義
3. **ルール**：AGENTS.md（規約・使ってよい技術・ディレクトリ構成・コマンド）
4. **完了の条件**：通すべきテスト・受け入れ基準

生成：`python3 <skill>/scripts/make_handoff.py docs/design.md "<コンポーネント名>" -o docs/handoff/<名前>.md`
（設計書の該当コンポーネント節とAPI節を抜き出し、`templates/handoff.md` の形式で出力する）

- 無関係なコード全体や、決まっていない仕様は渡さない。
- コンポーネントごとにセッション（エージェント）を分け、API契約だけでやりとりさせる（逆コンウェイ戦略）。
- APIファースト：契約を先に確定し、可能ならモックを用意してから並行で実装させる。
- 実装後、エージェントが**勝手に推測した箇所**を洗い出す。それは設計の穴なので、設計書に書き足すことを提案する。

## レビューモード

1. `python3 <skill>/scripts/check_design.py <設計書>` で機械的な不足を洗い出す（OpenAPIがあれば `check_openapi.py` も）。
2. `references/review-checklist.md` の観点で読み、各項目を **OK / 要修正 / 不明** で判定する。
3. 要修正には「どこを・どう直すか」を具体的に書く。重大度順（データ破壊・契約破り → 境界の崩れ → 読みやすさ）に並べる。
4. コードがすでにある場合は、設計と実装のずれ（他コンポーネントのDB直接参照、契約にないフィールド、層の飛び越え）も確認する。

出力形式：

```
## 設計レビュー結果
### 要修正（重大度順）
1. [項目] 問題 → 直し方
### 不明（ユーザーへの質問）
- ...
### OK
- ...
```

## 出力のしかた
- 設計書は `docs/design.md`、API契約は `docs/api/`、ADRは `docs/adr/NNNN-タイトル.md`、エージェント向けルールは `AGENTS.md`（Claude Code向けには `CLAUDE.md` から参照させてもよい）。
- 既存ファイルを書き換える前に差分の要点を示す。
- 不明点は推測で埋めず、最後に「確認したいこと」としてまとめる。
- 記入例が必要なら `examples/bookstore/` を参照する。
